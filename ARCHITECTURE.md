# Architecture and project map

This repository is a single Vite + React application that runs in the browser, backed by a Supabase Postgres database and optional push notifications through a Supabase Edge Function. The Worker deployment is Cloudflare static assets, and the app switches between student/admin flows and Root organizer tools at runtime.

## Runtime overview

At a high level, the app is structured like this:

- Browser app: React + Vite frontend in `src/`
- Supabase database: tables, RLS protection, data functions and migrations in `supabase/`
- Edge function: push notification sender in `supabase/functions/push/index.ts`
- Deployment: Cloudflare Worker serving the built `dist/` folder via `wrangler.jsonc`

## Frontend entry points

The main browser shell is `src/App.jsx`.

- It checks whether the app is configured (`isGeconfigureerd()` in `src/config.js`).
- If the URL starts with `/root`, it loads the Root organizer screen lazily from `src/root/RootApp.jsx`.
- Otherwise it loads the class/student-facing experience.

The root organizer is intentionally isolated from the regular student view and is only downloaded when needed. The app also keeps a separate `rootClient()` in `src/api.js` that creates a Supabase client for Root-authenticated flows, instead of loading the full Supabase client library for every student session.

## Core frontend areas

`src/` contains the app UI and domain logic for the student/admin experience:

- `src/App.jsx` — main app shell, route detection, session handling, global state
- `src/Login.jsx` — class login flow
- `src/KiesNaam.jsx` — choosing the student name after a valid class session
- `src/Rooster.jsx`, `src/Info.jsx`, `src/Stand.jsx`, `src/Meldingen.jsx` — main student screens
- `src/Beheer.jsx` and related files in `src/` — class admin management tools
- `src/editor/` — editor components used to build and preview class appearance and page content
- `src/root/` — Root organizer interface (`/root`): classes, programme, standings, templates, settings, safety

The actual UI is largely written in Dutch, but the repository documentation is currently kept in English, consistent with the project docs and the rest of the repo.

## Database and security model

The Supabase schema in `supabase/schema.sql` is written to enforce a strict access model:

- all public tables have RLS enabled,
- privileges are revoked from `anon` and `authenticated`,
- direct table access is intentionally not the app's primary path,
- the browser talks to the database through Postgres functions exposed via the Supabase RPC API.

The schema defines the core domain objects such as:

- `public.klassen` — class records and their unique slug
- `public.klas_wachtwoorden` — student/admin password hashes for each class
- `public.leerlingen` — student records inside a class
- `public.sessies` — class login sessions with token hash, role and expiry
- `public.activiteiten` — events/activities, dates and times
- `public.deelnames`, `public.dag_berichten`, `public.berichten`, `public.punten` — schedule and event information
- `public.push_abonnementen` — Web Push subscription data per student
- `public.root_gebruikers` — Supabase Auth users who have Root access

The schema also defines helper functions such as `_sessie`, `_beheer`, `_root_controle`, and app-level functions used by the frontend.

## Authentication and role model

There are two separate authentication systems in use:

1. Class sessions
   - A class login creates a session token tied to a `klas_id` and role.
   - The same token is used for student or class-admin actions.
   - Access checks happen through SQL functions in Supabase.

2. Root organizer access
   - Root users sign in through Supabase Auth using their own email/password account.
   - `public.maak_root('you@example.com')` promotes that Supabase Auth user to Root.
   - Optional MFA is checked via the `auth.mfa_*` flow and `public._root_controle()`.

This split is reflected in the app code:

- the student/admin flow uses the standard app RPC helper in `src/api.js`
- the Root flow uses `rootClient()` and `rootRpc()` in `src/root/client.js` and `src/api.js`

## Notification flow

Push notifications are supported by the Supabase Edge Function at `supabase/functions/push/index.ts`.

The function supports three main actions:

- `herinneringen`: scheduled reminder pushes generated by cron
- `handmatig`: manual push from Root or a class admin
- `test`: test push for a logged-in student/admin

The database stores subscriptions in `public.push_abonnementen`, and the actual VAPID configuration is kept server-side in Supabase secrets. The browser only needs the public VAPID key in `VITE_VAPID_PUBLIC_KEY`.

## Deployment architecture

The app is deployed as static assets behind a Cloudflare Worker.

The Cloudflare configuration lives in `wrangler.jsonc` and points to the `dist/` output directory:

- `npm run build` creates the frontend bundle
- `npx wrangler versions upload` creates a Worker preview
- `npx wrangler deploy` publishes the built assets to the configured Worker

This repository does not run a separate backend service in the Node app itself; the server-side behavior is provided by Supabase and Cloudflare/Wrangler, with the frontend compiled to static files.

## Typical request flow

A common class session path looks like this:

1. User opens the app and logs in to a class.
2. The frontend calls a Supabase RPC function through the REST endpoint.
3. The function validates the class session token and checks authorization.
4. The database returns the relevant data for the requested screen.
5. The React app renders the schedule, messages, standings or admin tools.

A Root organizer path is similar, but uses Supabase Auth and the Root RPC functions, with optional MFA enforced before access is granted.

## Documentation and change expectations

When changing the app, think in terms of the same boundaries used in the code:

- UI changes usually belong under `src/`
- Root-specific changes usually belong under `src/root/`
- database, RLS, security or migration changes belong under `supabase/`
- push behavior belongs under `supabase/functions/push/index.ts`
- deployment and environment changes belong under `wrangler.jsonc`, `CONFIGURATION.md` and related docs

The repository currently has no dedicated lint or test script in `package.json`; the project relies on building and direct verification of the relevant behavior in the running app.


## Texts

Every text shown to people lives in `src/teksten.js`. Components call `txt('Default text')` from `src/t.js`; the default text is the lookup key, and `teksten.js` holds the (editable) version. Texts with variables use `{name}` placeholders, for example `txt('Dag {dag}', { dag })`. `scripts/teksten.mjs` checks that every `txt()` call has an entry in `teksten.js` and can add missing ones (`npm run teksten:check`, `npm run teksten:sync`). Do not put user-visible text directly in components. Notification texts are the one exception (see `supabase/functions/push/index.ts`).
